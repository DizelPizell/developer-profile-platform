# ADR-0016: V1 читает только публичный GitHub с кредами приложения; токены пользователей не хранятся

- **Статус:** принято 2026-10-20
- **Релиз:** v1
- **Связано:** [0012](0012-github-oauth-only.md) — OAuth-вход; [0003](0003-github-token-encryption.md) — хранение токена; [0018](0018-github-sync-v1.md) — область синхронизации

## Контекст

Проекты платформы могут быть привязаны к GitHub-репозиториям. Нужно определить, как авторизовываться в GitHub API при синхронизации: от имени пользователя (его OAuth-токен) или от имени приложения (GitHub App / personal access token на аккаунте приложения).

Дополнительный вопрос: нужно ли хранить GitHub OAuth-токен пользователя для последующих запросов.

## Решение

V1 использует только публичный GitHub API (без OAuth-токена пользователя для API-запросов).

Все запросы к GitHub API при синхронизации делаются с credentials приложения (`GITHUB_APP_TOKEN` или `GITHUB_ACCESS_TOKEN` в `Settings`). Пользовательский OAuth-токен не хранится после первого входа.

Лимит requests-per-user = 7 на один POST-запрос синхронизации. Резерв воркера = 500 requests перед запуском (проверка при старте). Пауза в 10 минут между ручными синхронизациями одного репозитория.

Репозитории с `visibility = private` на GitHub не могут быть импортированы или синхронизированы в V1.

GitHub-токены никогда не логируются, никогда не возвращаются в API-ответах, никогда не передаются фронтенду.

## Отвергнуто

- **Хранить OAuth-токен пользователя для API** — нужна защищённая база хранения ([0003](0003-github-token-encryption.md)); риск утечки; не нужно для публичных репозиториев.
- **GitHub App с user-to-server токенами** — избыточно для V1 (только публичные данные).

## Последствия

Нет хранения пользовательских токенов — уменьшен attack surface. Лимиты rate limit — на учётную запись приложения, а не на пользователя. Приватные репозитории не поддерживаются в V1.
