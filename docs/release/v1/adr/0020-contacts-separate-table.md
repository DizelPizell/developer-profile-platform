# ADR-0020: Контакты хранятся в отдельной таблице; email и телефон отдаются только по клику

- **Статус:** принято 2026-11-06. Юридические вопросы не решены: до запуска их проверяет юрист (шаг 9.8; см. «Видимость и персональные данные»).
- **Релиз:** v1
- **Связано:** [0013](0013-profile-patch-origin-check.md) — дополняет: `PATCH /profile` и оба ответа профиля получают `contacts`, а правило «никогда не email» публичного DTO относится к `users.email`; [0015](0015-project-entities.md) — правила списка `technologies`; [0019](0019-public-github-on-cards.md) — до контактов все ссылки на публичной странице вели на известный хост; [0012](0012-github-oauth-only.md) — откуда берётся `users.email`.

_Правка 2026-11-10: текст возвращён к принятому решению (исходный ADR-020, коммит `4ac638a`). Предыдущая редакция этого файла при переписывании документации описала другое решение (`is_public`, типы `website`/`github`, авто-контакт GitHub, ручка `/contacts/reveal`) — это была фактическая ошибка._

## Контекст

V1 включает минимальные контакты, чтобы посетитель мог связаться с разработчиком (PRD, «V1 scope»; US-025). До этого решения было открыто: какие контакты есть, где они показываются и что значит «видимость контактов». Модели, контракта и макета не было.

Публичный профиль рендерится на сервере и доступен без сессии, его JSON-ручка открыта всем. Значение, попавшее в любой из них, доступно скрейперам и кешам поисковиков. Email и телефон — то, что люди меньше всего хотят отдавать массовому сбору.

Контакты — первые произвольные ссылки на публичной странице. До них каждая ссылка там вела на хост, известный платформе (`github.com`, ADR-0019).

## Решение

### Набор контактов

- По одному `EMAIL`, `TELEGRAM`, `LINKEDIN` и `PHONE`.
- До 3 `OTHER`: название и ссылка `http` или `https`. Кнопка в кабинете — «Другие способы связи».
- Не больше 7 позиций всего.
- Все необязательны. Требования к публикации профиля (ADR-0013) не меняются.

### Модель

Контакты — часть агрегата Profile. Таблица `profile_contacts`:

| Колонка | Тип | Примечание |
|---|---|---|
| `id` | UUID | PK |
| `profile_id` | UUID | FK → `profiles`, `ON DELETE CASCADE` |
| `type` | text | `EMAIL`, `TELEGRAM`, `LINKEDIN`, `PHONE` или `OTHER` |
| `value` | text | Нормализованное значение (см. «Валидация») |
| `label` | text, nullable | Название контакта `OTHER` |
| `position` | smallint | 1..7, порядок в списке |
| `created_at` | timestamp | |

Ограничения:

- CHECK на `type`.
- Частичный уникальный индекс `(profile_id, type) WHERE type <> 'OTHER'`: один стандартный контакт каждого типа.
- `label` обязателен для `OTHER` и `NULL` для остальных — CHECK.
- `UNIQUE (profile_id, position)` и `position BETWEEN 1 AND 7` ограничивают профиль семью строками, как диапазон позиций ограничивает технологии проекта (ADR-0015).
- CHECK длин: `value` по типу (см. «Валидация»), `label` до 40, ни одно не пустое.

Лимит 3 `OTHER` — доменное правило. БД держит потолок 7, но не 3.

Без `is_public`, `display_order` и `updated_at` у контакта: переключателя видимости нет (см. ниже), порядок — `position`, список заменяется целиком.

### Запись

- `contacts` — необязательное поле `PATCH /profile`. Отсутствует — список не меняется, список — заменяет целиком, `[]` — очищает, `null` — 422: правила `technologies` (ADR-0015).
- Элемент — `{type, value, label}`. `label` передаётся только для `OTHER`. `position` сервер ставит по порядку списка.
- Ручка сохраняет `SELECT ... FOR UPDATE` на строку профиля, поэтому два сохранения не перемежаются.
- Замена — явный `DELETE` перед `INSERT` в одной транзакции. Если оставить это unit of work, вставки могли бы выполниться первыми и нарушить `UNIQUE (profile_id, position)`.
- `profiles.updated_at` меняется, только если нормализованный список отличается от сохранённого (ADR-0013).

### Валидация

Для стандартных типов сервер хранит нормализованное значение и сам строит ссылку. Присланный пользователем URL для них не хранится, поэтому сохранённый стандартный контакт не может вести в другое место. Без новых зависимостей: email и телефон разбирает код платформы.

| Тип | Принимается | Хранится в `value` | Лимит | Ссылку строит сервер | Отклоняется |
|---|---|---|---|---|---|
| `EMAIL` | ASCII-адрес по `^[A-Za-z0-9._+-]+@[A-Za-z0-9-]+(\.[A-Za-z0-9-]+)*\.[A-Za-z]{2,}$` | Адрес с доменом в нижнем регистре | 254 | `mailto:{value}` | `?`, `&`, `%`, пробелы, кириллические домены и любой другой не-ASCII |
| `TELEGRAM` | `name`, `@name`, `t.me/name`, `https://t.me/name`, с необязательным `/` в конце | `name`, в написании пользователя | 5–32 | `https://t.me/{name}` | Другие хосты, инвайты (`t.me/+…`, `t.me/joinchat/…`), более глубокие пути, query, зарезервированные пути Telegram |
| `LINKEDIN` | `linkedin.com/in/{slug}` с `https://`, `www.` или региональным поддоменом и необязательным `/` | `slug` | 3–100 | `https://www.linkedin.com/in/{slug}` | Другие хосты — сравнение точное, не по суффиксу (`linkedin.com.evil.example`, `linkedin.com@evil.example`), `/company/` и другие пути, query |
| `PHONE` | `+` и цифры; пробелы, дефисы и скобки удаляются | E.164 по `^\+[1-9]\d{7,14}$` (8–15 цифр) | 16 | `tel:{value}` | Номер без `+`. `8…` не переписывается в `+7…` |
| `OTHER` | URL `http`/`https`, в хосте есть точка; название — простой текст | URL со схемой в нижнем регистре; название — в `label` | URL 2048, название 40 | Сохранённый URL | Любая другая схема (`javascript:`, `data:`), логин в URL, управляющие символы, пробелы, обратный слеш |

- Каждое значение обрезается. Пустой `value` — ошибка, а не удалённый контакт: форма не отправляет пустые строки.
- `label` проходит через `plain_text` (ADR-0013) и выводится как текст.
- Сервер никогда не запрашивает эти URL: ни превью, ни проверок. Поверхности для SSRF нет.
- Ошибки — в существующем формате: `loc` `["body", "contacts", <index>, "value"]` или `"label"`, и `["body", "contacts"]` для повтора типа или лишних элементов. Введённые значения не возвращаются (ADR-0013).

#### Что говорят правила сервисов

Проверено по официальной документации 2026-11-06; зарезервированные пути Telegram — 2026-11-10.

| Сервис | Подтверждено | Источник |
|---|---|---|
| Telegram | Имена: `A-z` (без учёта регистра), `0-9` и подчёркивание; 5–32 символа | https://core.telegram.org/method/account.checkUsername, https://telegram.org/faq |
| Telegram | Публичная ссылка — `t.me/<username>`. `t.me/+<hash>` и `t.me/joinchat/<hash>` — инвайты, `t.me/+<phone_number>` — номер телефона; служебные пути не являются именами | https://core.telegram.org/api/links |
| LinkedIn | Custom URL — 3–100 символов, без учёта регистра, без пробелов, символов, спецсимволов и слова LinkedIn | https://www.linkedin.com/help/linkedin/answer/a542685 |

Зарезервированные пути Telegram (со страницы links, 2026-11-10), сравниваются без учёта регистра: значения, запрещённые для `<username>.t.me` — `addemoji`, `addlist`, `addstickers`, `addstyle`, `addtheme`, `auction`, `auth`, `boost`, `call`, `confirmphone`, `contact`, `giftcode`, `invoice`, `joinchat`, `login`, `m`, `nft`, `proxy`, `setlanguage`, `share`, `socks`, `web`, `a`, `k`, `z`; и первые сегменты форматов ссылок — `newbot`, `oauth`, `bg`, `msg`, `c`. Короткие значения и `+`/`$` и так не проходят правило 5–32 символов. Список — константа `TELEGRAM_RESERVED` в `backend/app/profile/contacts.py`; при появлении новых форматов его обновляют вручную.

Допущения — документация их не закрывает:

- **Telegram**: может ли имя начинаться с цифры или `_`, содержать повторные или завершающие `_`. Принимается всё, что разрешает подтверждённое правило; более строгих правил наугад не добавляем.
- **Telegram**: `telegram.me`, `http://t.me` и `<name>.t.me` не принимаются — таблица выше их не называет.
- **LinkedIn**: допустимые символы не перечислены. Slug принимается по `^[A-Za-z0-9-]{3,100}$`, с дефисами, потому что сгенерированные адреса профилей, по допущению, их используют.
- **LinkedIn**: страница помощи не показывает путь `/in/`. `https://www.linkedin.com/in/{slug}` — решение владельца и допущение о сервисе.
- **LinkedIn**: «региональный поддомен» — ровно две латинские буквы (`de.linkedin.com`). Это допущение.
- **LinkedIn**: адреса на нелатинице отклоняются допущенным шаблоном. Есть ли такие у реальных профилей — не подтверждено.

### Угрозы

| Угроза | Мера |
|---|---|
| Подмена домена в стандартном контакте (`linkedin.com.evil.example`, `linkedin.com@evil.example`) | Хосты сравниваются точно; хранится только имя или slug; ссылку строит сервер |
| `javascript:` или `data:` в ссылке | `OTHER` допускает только `http` и `https` — на сервере. Фронтенд повторяет проверку по типу, как `isGitHubUrl`; не прошедшая ссылка остаётся простым текстом |
| Инъекция в `mailto:` (`a@b.c?bcc=x`) | В шаблоне адреса нет `?`, `&`, `%`, поэтому ссылка не требует экранирования и не несёт параметров |
| Массовый сбор email и телефона | Их значений нет ни в серверном HTML, ни в JSON публичного профиля. Они приходят из отдельной ручки по клику (см. «Видимость и персональные данные»), с rate limit из шага 8.3 |
| Утечка через props | Клиентский компонент не получает значение: prop клиентского компонента сериализуется в HTML. Значение запрашивается по клику |
| Вводящее в заблуждение название (`OTHER` «GitHub», ведущий в другое место) | Рядом с названием показывается хост, прочитанный через `new URL` (IDN — в punycode). Название — текст разработчика с пометкой «От автора» |
| Open redirect | Редиректора нет: ссылки ведут прямо на цель |
| Ссылочный спам для поисковиков | `rel` включает `nofollow ugc` |
| Tabnabbing и утечка referrer | `target="_blank"` с `rel="noopener noreferrer nofollow ugc"`. У `tel:` и `mailto:` нет `target` |
| Разметка в названии или значении | Выводится как текст React, никогда как HTML |
| Значения в логах | Тела запросов не логируются, ответы с ошибками не повторяют ввод, строки логов фронтенда называют только поля |

### Видимость и персональные данные

- **Публично**: `TELEGRAM`, `LINKEDIN` и `OTHER` — с `value` и `url` в `PublicProfileResponse` и в серверном HTML.
- **По запросу**: `EMAIL` и `PHONE` перечислены в `PublicProfileResponse` с `value` и `url`, равными `null`, чтобы страница знала об их наличии. Значение приходит из `GET /public/profiles/{slug}/contacts?type=EMAIL|PHONE`.
- Без JavaScript email и телефон не видны. Это принято.
- **Переключателя видимости в V1 нет.** «Видимость контактов» (PRD) значит, что разработчик добавляет или удаляет контакт, а контакты следуют состоянию профиля. Скрытый контакт в V1 никто бы не читал — это были бы персональные данные без читателя. Переключатель можно добавить позже nullable- или default-колонкой.
- **Профиль `PRIVATE`**: контакты редактируются; публично профиль и новая ручка отвечают 404.
- **Профиль `PUBLISHED`**: сохранённый контакт сразу публичен. Черновика нет — форма об этом предупреждает.
- **`users.email`** приходит из GitHub (ADR-0012). Он никогда не публикуется и не заполняет контакт. Email контакта — отдельное значение, которое вводит разработчик.
- Удаление контакта удаляет строку. Удаление пользователя удаляет контакты каскадом.

До запуска нужна проверка юриста (9.8). Юридических выводов этот ADR не делает:

- нужно ли согласие на публикацию телефона или email, в какой форме, нужно ли хранить отметку и её дату;
- что должна говорить политика персональных данных и где она публикуется;
- как человек может потребовать прекратить распространение и достаточно ли удаления контакта и скрытия профиля;
- кто оператор;
- применяются ли требования локализации к хостингу, выбранному в 9.1 и 9.3;
- что делать с контактом, принадлежащим другому человеку.

Эти вопросы не блокируют C.1. Если согласие нужно хранить, его добавит отдельная миграция. Их несут шаги 9.7 и 9.8.

### API и контракт

| Изменение | Совместимость |
|---|---|
| `ProfileUpdate.contacts`: необязательное | Существующие клиенты не затронуты |
| `OwnProfileResponse.contacts`: обязательный список `{type, value, label, url}` | Текущий фронтенд его игнорирует |
| `PublicProfileResponse.contacts`: обязательный список `{type, value, label, url}`, `value` и `url` = `null` для `EMAIL` и `PHONE` | Текущий фронтенд отбрасывает неизвестные поля |
| `GET /public/profiles/{slug}/contacts?type=EMAIL\|PHONE` → `{type, value, url}` | Новая ручка |

- `url` строит сервер; для `OTHER` он равен `value`.
- Новой ручке не нужна сессия. Она возвращает только запрошенное значение с `Cache-Control: no-store`.
- Приватный, отсутствующий или некорректный профиль либо профиль без такого контакта — тот же 404, что у `GET /public/profiles/{slug}`. `type` кроме `EMAIL` и `PHONE` — 422 `VALIDATION_ERROR`.
- `PUT` не используется: CORS разрешает `GET`, `POST`, `PATCH`, `DELETE` и `OPTIONS` (ADR-0013, ADR-0015).
- Публичный профиль делает на один запрос больше — для любого числа контактов.
- Базовый уровень Redocly для `docs/api/openapi.yaml` (`@redocly/cli@1.34.0`) — 3 ошибки и 36 предупреждений — не растёт: у новой операции `operationId`, `security: []` и ответ 404.

### Фронтенд (C.2)

- Секция «Контакты» на публичной странице с пометкой «От автора» и кнопка в hero, ведущая к ней. Без контактов ни то ни другое не рендерится. Место на странице — по макету.
- `TELEGRAM`, `LINKEDIN` и `OTHER` рендерятся на сервере. `OTHER` показывает название и хост.
- «Показать email» и «Показать телефон» — один небольшой клиентский компонент. Он запрашивает значение только по клику, состояния: ожидание, загрузка, показано, ошибка. Получает тип и slug, никогда значение.
- В кабинете блок стоит в форме профиля и сохраняется кнопкой «Сохранить»: четыре фиксированных поля, затем строки «Других способов связи» (название, ссылка, удалить). На лимите кнопка неактивна с подсказкой. Подсказка говорит, что контакты видны всем, пока профиль опубликован.
- Форма отправляет весь список, если он изменился, и показывает нормализованные значения из ответа.
- `profileFieldErrors` сейчас читает только `loc` длины 2 и должен научиться путям контактов.
- Публичный ридер следует F-GH2: отсутствующий `contacts` — `[]` без лога; неверная форма — `[]` с одной строкой лога на профиль, с именем поля и без значений. Остальной профиль продолжает работать.
- Макета контактов нет. C.2 начинается после него.

## Отвергнуто

- **Колонки в `profiles` для четырёх типов плюс таблица для `OTHER`** — список и его ошибки всё равно нужны, получилось бы два механизма.
- **JSON-колонка в `profiles`** — БД не держала бы правила, а ADR-0013 дублирует инварианты в БД.
- **Все значения в публичном JSON и HTML** — их может массово прочитать кто угодно.
- **Обфускация в HTML** — вредит доступности и бесполезна, пока JSON открыт.
- **`email-validator` и `phonenumbers`** — зависимости ради двух полей; строгий ASCII-шаблон заодно закрывает инъекцию в `mailto:`.
- **Отдельный `PUT /profile/contacts`** — `PUT` нет в CORS, а у формы одно сохранение.
- **Переключатель видимости на каждый контакт** — отвергнут для V1, см. «Видимость и персональные данные».

## Последствия

Плюсы:

- Посетитель может связаться с разработчиком с публичной страницы.
- Стандартный контакт может вести только на сервис, который он называет.
- Email и телефон не попадают в HTML страницы, публичный JSON и кеши поисковиков.
- Одна таблица и один путь записи для всех типов; новый тип — это CHECK и валидатор.

Минусы:

- Без JavaScript email и телефон недоступны.
- До шага 8.3 у новой ручки нет rate limit, и скрипт может читать значения по одному профилю (в коде — комментарий `shortcut:`). Бот с JavaScript сможет то же после 8.3, медленнее. Мера уменьшает массовый сбор, но не предотвращает его.
- Публичный ответ раскрывает, что email или телефон существует.
- Адреса с кириллическими доменами и номера без `+` отклоняются.
- Лимит 3 `OTHER` держится только на доменном слое.
- Форма получает список и ошибки строк — сложнее набора простых полей.

## Риски

- Допущения о Telegram и LinkedIn (см. «Что говорят правила сервисов») могут отклонить реальные имена или slug. Проверка — первые реальные профили; если отказ подтвердится, правило расширяется в `backend/app/profile/contacts.py` и в CHECK длины, если затронут лимит.
- Telegram добавляет новые служебные пути; имя, совпавшее с новым путём, пройдёт проверку и даст неработающую ссылку. Список сверяется со страницей links при правках контактов.

## Не входит

- `CONTACT_CLICK` и любая аналитика контактов (V1.1, фаза 7).
- Переключатель видимости на контакт.
- Согласие в модели.
- Сам rate limit (шаг 8.3).
- Редиректор и превью ссылок.

## Открытые вопросы

- Юридические вопросы из «Видимости и персональных данных» (9.7, 9.8).
- Место секции на публичной странице — в макете.
