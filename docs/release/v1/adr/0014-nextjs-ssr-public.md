# ADR-0014: Фронтенд — Next.js App Router с SSR для публичных страниц

- **Статус:** принято 2026-10-01
- **Релиз:** v1
- **Связано:** [0019](0019-public-github-on-cards.md) — публичные данные GitHub на карточках

## Контекст

Платформа имеет два типа страниц с разными требованиями: публичные профили (SEO-критичны, индексируются поисковиками) и кабинет разработчика (SPA-поведение, частые мутации).

## Решение

Next.js App Router. TypeScript. Tailwind CSS + shadcn/ui.

Публичные страницы (`/u/[slug]`, `/u/[slug]/projects/[id]`) — Server Components, рендерятся на сервере. Данные запрашиваются в Server Components напрямую из бэкенд-API. Нет client-side fetch на первый render.

Кабинет (`/me/*`) — Client Components там, где нужна интерактивность, Server Components для начального рендера данных.

Явное разделение публичного и приватного API-контракта: публичные эндпоинты (`GET /api/v1/profiles/{slug}`) используются фронтом без аутентификации.

Общее правило: предпочитать Server Components, переходить на Client Components только при необходимости интерактивности.

## Отвергнуто

- **SPA без SSR** — плохо для SEO публичных профилей; медленный первый рендер.
- **Remix** — команда владеет Next.js; нет преимуществ, оправдывающих переход.

## Последствия

Публичные страницы индексируются сразу. SSR усложняет кэширование — нужно явно управлять `cache` и `revalidate`. Одна база для публичных и приватных страниц без дублирования кода.
