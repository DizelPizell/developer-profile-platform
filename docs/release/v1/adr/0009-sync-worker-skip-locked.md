# ADR-0009: Воркер синхронизации работает как отдельный процесс с PostgreSQL SKIP LOCKED

- **Статус:** принято 2026-10-10; уточнено [0018](0018-github-sync-v1.md)
- **Релиз:** v1
- **Связано:** [0008](0008-no-kafka-v1.md) — почему не Kafka; [0018](0018-github-sync-v1.md) — триггеры, лимиты, статус

## Контекст

[0008](0008-no-kafka-v1.md) решил, что синхронизация GitHub в V1 асинхронная, без Kafka. Конкретный механизм был оставлен открытым. Нужен механизм, который: надёжно не обработает одну джобу дважды, переживает рестарт процесса, не требует новой инфраструктуры.

## Решение

Воркер — отдельный процесс (не FastAPI BackgroundTasks), опрашивает `github_sync_jobs` через `SELECT ... FOR UPDATE SKIP LOCKED`.

Одна строка `github_sync_jobs` — один логический запрос синхронизации. Автоматические ретраи переиспользуют ту же строку и увеличивают `attempt_count`. Новая строка создаётся только для нового запроса после того, как предыдущий достиг терминального состояния.

`github_sync_jobs` — единственный источник истины о статусе синхронизации. `github_repositories` не дублирует статус, timestamps или ошибки джобов.

Частичный уникальный индекс `uq_github_sync_jobs_active` на `github_repository_id` WHERE status IN ('QUEUED', 'SYNCING') — не более одной активной джобы на репозиторий.

Настройки (стартовые значения, конфигурируемые): 5 попыток, опрос 5 с, базовая задержка ретрая 30 с, максимальная 30 мин, порог стале-SYNCING 10 мин.

Watchdog возвращает зависшие `SYNCING`-джобы в `QUEUED` с тем же лимитом попыток и защитой `SKIP LOCKED`.

## Отвергнуто

- **FastAPI BackgroundTasks** — не переживает рестарт процесса.
- **Kafka/Outbox** — уже отклонено в [0008](0008-no-kafka-v1.md).

## Последствия

Нет новой инфраструктуры. `SKIP LOCKED` позволяет горизонтальное масштабирование (в V1 — один процесс). Единый источник истины о статусе исключает класс dual-write ошибок. Нужен watchdog — логика, которой не было бы в broker-based архитектуре.
