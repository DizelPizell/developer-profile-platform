# ADR-0024: Rate limit считается в процессе бэкенда, в памяти, по IP

- **Статус:** принято 2026-11-19
- **Релиз:** v1
- **Связано:** [0020](0020-contacts-separate-table.md) — ручка раскрытия контактов ждала лимита из шага 8.3; [0021](0021-single-origin-behind-nginx.md) — IP клиента бэкенд берёт из `X-Forwarded-For` только от Nginx; [0012](0012-github-oauth-only.md) — вход и callback

## Контекст

`GET /public/profiles/{slug}/contacts` отдаёт email и телефон без сессии. Без лимита скрипт перебирает профили и собирает значения (ADR-0020, «Минусы»). Callback входа на каждый запрос с верным `state` обменивает `code` в GitHub, а `state` проверяется только по cookie, которую скрипт подставит сам.

Лимит по IP имеет смысл только на ручках, которые вызывает браузер: SSR ходит в API с адреса контейнера фронтенда (ADR-0021). Продакшн — один хост, один процесс uvicorn (`--workers` не задан).

## Решение

1. **Модуль `backend/app/rate_limit.py`**: `RateLimiter` с фиксированными окнами, выровненными по часам, словарь в памяти процесса под `threading.Lock` (синхронные ручки идут в пуле потоков). Запрос засчитывается, только если прошёл все окна: заблокированный клиент освобождается в конце окна. Окна, которые уже кончились, вычищаются, когда записей больше 10 000.
2. **Ключ — IP из `request.client.host`**: uvicorn подставляет его из `X-Forwarded-For` только для запросов от Nginx (`FORWARDED_ALLOW_IPS`, ADR-0021).
3. **Лимиты:**
   - раскрытие контакта: 10 в минуту и 50 в час с одного IP — `contacts_limiter`. Считаются все ответы, включая `404`: перебор slug ограничен так же;
   - вход: 20 в минуту с одного IP, общий счётчик на `GET /auth/github/login` и `GET /auth/github/callback` — `login_limiter`. Один вход — два запроса. Callback считает до проверки `state`.
4. **Ответ:**
   - контакты — `429 RATE_LIMITED` в общем формате ошибок и `Retry-After` в секундах;
   - вход и callback — переход браузера, поэтому редирект `{FRONTEND_URL}/login?error=RATE_LIMITED`, как остальные ошибки callback; `oauth_state` не выдаётся. Экран входа показывает «Слишком много попыток входа. Подождите минуту и попробуйте снова.»
5. Фронтенд кнопки «Показать email» не меняется: на `429` он показывает общий текст ошибки и «Повторить».

## Отвергнуто

- **`limit_req` в Nginx** — почти без кода, но ответ не в формате API и без `request_id`, в разработке лимита нет, проверка только через `check_nginx.sh`.
- **Счётчики в PostgreSQL** — переживают перезапуск и несколько процессов, но это запись в базу на каждый публичный запрос ради одного хоста с одним процессом.
- **Redis** — новая инфраструктура, в V1 не используется.
- **Лимит на запись в кабинете** — там нужны сессия и Origin, на GitHub-ручках уже есть бюджет пользователя (ADR-0018).

## Последствия

- Перезапуск бэкенда обнуляет счётчики. Лимит замедляет массовый сбор, но не предотвращает его (как и записано в ADR-0020).
- Посетители за одним NAT делят лимит. 10 раскрытий в минуту обычный посетитель не тратит.
- Тесты обнуляют счётчики перед каждым тестом (`tests/conftest.py`).
- Решение пересматривается, если появится `--workers > 1` или второй хост: с N процессами реальный лимит в N раз выше. Тогда — счётчики в PostgreSQL или `limit_req` в Nginx.
