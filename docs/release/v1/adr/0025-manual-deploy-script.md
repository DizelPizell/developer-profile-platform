# ADR-0025: Выкладка — скрипт `deploy.sh` на сервере, запускаемый вручную; CI проверяет каждый PR

- **Статус:** принято 2026-11-19
- **Релиз:** v1
- **Связано:** [0021](0021-single-origin-behind-nginx.md) — один хост с Compose, образы собираются на нём; [0022](0022-media-on-host-volume.md) — том `media` бэкапится вместе с базой

## Контекст

До шага 9.4 выкладка — две команды из `DEPLOY.md`: `git pull` и `docker compose up -d --build`. Они не предупреждают, что в обновлении есть миграция (миграции не откатываются, перед ними нужен бэкап), не проверяют, что сайт после выкладки отвечает, и не запоминают, на какой коммит откатываться.

В CI три workflow с фильтрами `paths:`. Образ бэкенда, на котором работают `backend`, `migrate` и `github-worker`, в CI не собирался: сломанный `Dockerfile` выяснился бы только на сервере. `main` не защищена: слить в неё можно без зелёных проверок, а обязательной проверка с фильтром `paths:` быть не может — PR, где workflow не запустился, ждёт её вечно.

Владелец один, хост один, выкладки — несколько в месяц.

## Решение

1. **Выкладка — `deploy.sh` в корне репозитория**, его запускает владелец на сервере по SSH:
   - `./deploy.sh` — на `origin/main`, `./deploy.sh <commit>` — на коммит;
   - если между текущим и новым коммитом менялся `backend/alembic/versions/`, скрипт останавливается без `--with-migrations`: флаг — подтверждение, что бэкап сделан (автоматический бэкап добавит 9.5);
   - запоминает текущий коммит в `.deploy/previous`, переходит на новый (`checkout --detach`), запускает `docker compose up -d --build`;
   - ждёт до 60 секунд `200` от `/api/v1/health` и `/` через Nginx на хосте (`--resolve` на `127.0.0.1`, `-k`: до первого сертификата Let's Encrypt он самоподписанный); не дождался — выход с ошибкой;
   - `./deploy.sh --rollback` — на коммит из `.deploy/previous`; если между ними миграция, отказ: откат с миграцией — восстановление из бэкапа.
2. **CI проверяет каждый PR**: у `pull_request` нет фильтров `paths:` (у `push` остались), поэтому все проверки можно сделать обязательными. Старый прогон PR отменяется новым (`concurrency`), прогоны на `main` доходят до конца. В `backend.yml` собирается образ бэкенда. `deploy.sh` проходит `shellcheck` и `.github/scripts/check_deploy.sh` — прогон на временном репозитории с заглушками `docker` и `curl`.
3. **`main` защищена** в настройках GitHub: слияние только через PR и только с зелёными обязательными проверками. Скрипт выкладывает `origin/main` и CI на сервере не проверяет — он опирается на эту защиту.

## Отвергнуто

- **Выкладка из GitHub Actions по SSH:** в секретах GitHub появляется ключ к продакшн-хосту — взлом аккаунта или workflow даёт доступ к серверу. Решает проблему частых релизов в команде, которой нет.
- **Образы в реестре (GHCR), сервер их скачивает:** реестр, теги и токен для pull ради одного хоста. Даёт откат без пересборки и снимает сборку Next.js с сервера — это и будет поводом к нему.
- **Оставить две команды в `DEPLOY.md`:** без проверки миграций и ответа сайта ошибка выкладки замечается пользователями.

## Последствия

- Секретов для доступа к серверу вне сервера нет.
- Образы собираются на продакшн-хосте: сборке Next.js нужно 1–2 ГБ памяти, на маленькой VPS — swap.
- Откат — пересборка прошлого коммита, минуты, а не секунды.
- PR только с документацией тоже ждёт всех проверок — несколько минут CI.
- После первого `deploy.sh` checkout на сервере в состоянии detached HEAD; `git pull` больше не используется.

Решение пересматривается: на выкладку из Actions — если выкладок станет больше нескольких в неделю или появится второй человек; на реестр образов — если сервер перестанет вытягивать сборку или понадобится откат за секунды.
