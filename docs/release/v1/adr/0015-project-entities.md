# ADR-0015: Проект хранит текст, технологии и витрину как самостоятельные сущности

- **Статус:** принято 2026-10-05
- **Релиз:** v1
- **Связано:** [0004](0004-contribution-as-fields.md), [0005](0005-project-lifecycle-visibility.md), [0017](0017-repository-linking.md)

## Контекст

Профиль разработчика строится вокруг проектов. Проект должен поддерживать: несколько технологий (многие-ко-многим), витрину на профиле (не более 3), разные типы работ (коммерческая, фриланс, образование, открытый код, NDA). Нужно решить, как моделировать эти данные.

## Решение

Агрегат `Project` состоит из трёх сущностей:

1. **`projects`** — основная таблица: `id`, `user_id`, `title`, `description`, `role`, `contribution`, `status`, `visibility`, `slug`, `created_at`, `updated_at`.
2. **`project_technologies`** — связь многие-ко-многим с `technologies` (нормализованный список технологий).
3. **`featured_projects`** — порядок проектов в витрине профиля; максимум 3 записи на пользователя (инвариант бэкенда, не только UI).

`project_type` не реализован в V1 — типы работ различаются через текстовые поля (`role`, `contribution`).

NDA-проект: `visibility = PRIVATE` — не показывается публично, но разработчик видит его в кабинете.

Slug проекта уникален в рамках пользователя (`unique(user_id, slug)`).

Лимит витрины в 3 проекта проверяется в domain-слое перед записью — не только в API-валидации.

## Отвергнуто

- **Поле `technologies` как JSON-массив** — нельзя нормализовать, нет агрегации по технологиям.
- **Порядок витрины через поле в `projects`** — смешивает данные профиля с данными проекта.

## Последствия

Технологии нормализованы — можно считать и агрегировать. Витрина отдельная — легко управляется и имеет инвариант на уровне домена. Slug уникален на пользователя — нет глобальных конфликтов.
