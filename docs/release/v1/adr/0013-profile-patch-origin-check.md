# ADR-0013: Профиль редактируется через PATCH; все изменения состояния защищены Origin-проверкой

- **Статус:** принято 2026-10-01
- **Релиз:** v1
- **Связано:** [0012](0012-github-oauth-only.md) — сессии; [0015](0015-project-entities.md) — проекты используют тот же паттерн

## Контекст

При серверных сессиях в cookie браузер автоматически отправляет cookie на любой запрос к домену. Классическая CSRF-атака использует это: вредоносная страница делает POST на API и браузер прикладывает cookie жертвы. Нужна CSRF-защита без добавления токенов в тело запроса.

## Решение

CSRF-защита через проверку заголовка `Origin` на всех state-changing запросах (POST, PATCH, DELETE, PUT).

Допустимые origins задаются через `ALLOWED_ORIGINS` в `Settings`. Запрос без `Origin` или с недопустимым `Origin` → `403 Forbidden`.

Редактирование профиля через `PATCH /api/v1/me/profile` — частичное обновление, только переданные поля. Публикация профиля — отдельный эндпоинт `POST /api/v1/me/profile/publish` (не поле в PATCH). Непубликация — `POST /api/v1/me/profile/unpublish`.

Права проверяются на бэкенде: только владелец профиля может его редактировать. Публичные эндпоинты (`GET /api/v1/profiles/{slug}`) не требуют аутентификации.

## Отвергнуто

- **CSRF-токены в форме** — сложнее интегрировать с SPA, нет преимуществ перед Origin-check при правильном SameSite.
- **Double Submit Cookie** — излишне при наличии Origin-check и SameSite=Lax.

## Последствия

Простая и эффективная CSRF-защита. Origin-check нужно проверять для всех state-changing эндпоинтов — middleware, а не на каждом роутере. `ALLOWED_ORIGINS` нужно настраивать в каждой среде.
