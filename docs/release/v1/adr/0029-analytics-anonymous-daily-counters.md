# ADR-0029: Аналитика — анонимные дневные счётчики событий от браузера, без IP и cookie посетителя

- **Статус:** предложено 2026-11-20
- **Релиз:** v1 (фаза 7, V1.1)
- **Связано:** [0024](0024-rate-limit-in-process.md) — лимит приёма событий тем же `RateLimiter`; [0013](0013-profile-patch-origin-check.md) — Origin-проверка запросов, меняющих состояние; [0028](0028-account-deletion-hard-and-immediate.md) — счётчики удаляются каскадом с аккаунтом; [0023](0023-demo-link-without-iframe.md) — клики по демо; [0020](0020-contacts-separate-table.md) — `CONTACT_CLICK` и персональные данные

## Контекст

Фаза 7 (V1.1) даёт разработчику пять событий: `PROFILE_VIEW`, `PROJECT_VIEW`, `DEMO_CLICK`, `GITHUB_CLICK`, `CONTACT_CLICK` и воронку «профиль → проект → демо/GitHub → контакт» (PRD, ARCHITECTURAL_DIALOGUE §22). Не решено, какие метаданные собирать, сколько их хранить и нужно ли согласие посетителя.

Ограничения:
- юриста нет, и юридическая часть уже держит запуск (scope-v1, «Открытые вопросы»). `/privacy` сейчас говорит, что аналитики и трекеров нет;
- аналитика некритична: её отказ не должен мешать открыть профиль или перейти на демо (CLAUDE.md);
- рейтингов и оценок нет, цифры видит только владелец профиля;
- публичные страницы рендерятся на сервере; SSR ходит в API с адреса контейнера фронтенда (ADR-0021);
- один хост, один процесс uvicorn, лимиты в памяти (ADR-0024).

## Решение

1. **Посетитель не идентифицируется.** Не сохраняются IP, User-Agent, referrer, cookie и идентификаторы в `localStorage`. Персональных данных посетителя в аналитике нет, поэтому баннер согласия не нужен. IP используется только в памяти — как ключ лимита (п. 6), как и сейчас для контактов.
2. **Хранятся дневные счётчики, а не события.** Таблица `analytics_daily_counts`:
   - `id`, `profile_id` (FK → `profiles`, `ON DELETE CASCADE`), `project_id` (nullable, FK → `projects`, `ON DELETE CASCADE`), `event_type` (`PROFILE_VIEW | PROJECT_VIEW | DEMO_CLICK | GITHUB_CLICK | CONTACT_CLICK`), `day` (`date`, UTC), `count` (`integer`, > 0);
   - `UNIQUE NULLS NOT DISTINCT (profile_id, project_id, event_type, day)` — PostgreSQL 17 это умеет, запись — `INSERT … ON CONFLICT … DO UPDATE SET count = count + 1`;
   - CHECK: `PROJECT_VIEW` и `DEMO_CLICK` — с `project_id`; `PROFILE_VIEW` и `CONTACT_CLICK` — без; `GITHUB_CLICK` — с `project_id` для ссылки на репозиторий проекта, без него для ссылки на профиль GitHub в шапке.

   Строки не личные, срока хранения и задачи очистки нет: счётчики живут, пока жив профиль или проект, и удаляются каскадом (ADR-0028).
3. **Один путь приёма — от браузера.** `POST /api/v1/analytics/events`, тело `{"type": "...", "slug": "...", "project_id": "<uuid>" | null}`:
   - `202` без тела, если событие засчитано **или молча отброшено**: профиль не `PUBLISHED`, проект не `PUBLISHED` + `PUBLIC`, проект другого профиля, `project_id` не там, где его требует CHECK. Один ответ не выдаёт, существует ли закрытый проект;
   - `422 VALIDATION_ERROR` — тело не той формы (ошибка фронтенда, а не данные);
   - `429 RATE_LIMITED` — п. 6.
4. **Фронтенд отправляет и забывает:** `fetch` с `keepalive: true` и `credentials: "include"`, без ожидания ответа и без показа ошибок. Просмотр — после монтирования публичной страницы профиля или проекта; клик — в обработчике ссылки, переход не ждёт запроса. `sendBeacon` не берём: с телом `application/json` на другой origin (в разработке API на другом порту) браузеры его не отправляют.
5. **Просмотры не считаются при SSR**, только маячком из браузера: SSR вызывают боты, prefetch и повторные рендеры, а большинство ботов не выполняет JS и отсеивается само. Отдельного фильтра ботов по User-Agent нет.
6. **Лимит:** `events_limiter` в `backend/app/rate_limit.py`, 60 событий в минуту с одного IP. Посетитель на одной странице шлёт единицы событий.
7. **Свои просмотры не считаются:** если в запросе есть действующая сессия владельца профиля, событие отбрасывается с `202`. Остальные пользователи с сессией считаются как анонимные.
8. **Origin-проверка (ADR-0013) не меняется:** `fetch` с того же фронтенда несёт верный `Origin`. Запрос без сессии разрешён: это публичная ручка, как раскрытие контактов.
9. **Чтение (шаг 7.2)** — только владельцу, по сессии: `GET /api/v1/analytics/profile` (суммы по типам и по проектам) и `GET /api/v1/analytics/projects/{id}` (по дням), за последние N дней. Период и форма ответа — в 7.2. _Правка 2026-11-20 (7.2): период — 7, 30 или 90 дней UTC, сегодня включительно, по умолчанию 30; счётчики — поля `profile_views`, `project_views`, `demo_clicks`, `github_clicks`, `contact_clicks`; в профиле — все свои проекты с нулями, в проекте — каждый день периода с нулями. Отдельного поля воронки нет: её этапы — суммы `totals`._ Воронка — суммы событий каждого этапа за период, **не конверсия людей**: экран (7.4) пишет это прямо.
10. **`/privacy`** правится в шаге 7.3, вместе с началом отправки: считаются просмотры и клики без IP, cookie и данных о посетителе, только суммы за день.

## Отвергнуто

- **Ежедневный хэш IP + User-Agent с солью (как у Plausible)** — дал бы уникальных посетителей за день, но IP всё равно обрабатывается, а без юриста это лишний риск. Кода больше: соль, её смена, хранение хэшей. Возвращается, если владелец решит, что уникальные посетители стоят этого.
- **Cookie или идентификатор посетителя в `localStorage`** — нужно согласие посетителя; ради счётчиков не стоит.
- **Сырые события (`analytics_events`)** с временем и метаданными — пригодились бы для источников переходов и разбивки по часам, но тогда нужны срок хранения и задача очистки. Ни один вопрос V1.1 их не требует. Название `analytics_events` из `DATABASE_SCHEMA.md` заменено.
- **Подсчёт просмотров в SSR или в Nginx-логах** — п. 5; разбор логов — ещё и новый процесс.
- **`CONTACT_CLICK` на сервере в ручке раскрытия контактов** — покрыл бы только email и телефон, а ссылки на Telegram и другие — обычные `<a>`. Два пути для одного события.
- **Внешний сервис аналитики** — данные посетителей уходят третьей стороне, а ей нужна cookie или IP.

## Последствия

- Нет уникальных посетителей и конверсии по людям: один человек, обновивший страницу пять раз, — пять просмотров. Это видно на экране аналитики.
- Счётчики можно накрутить скриптом в пределах лимита. Рейтингов нет, цифры видит только владелец: накрутка вводит в заблуждение только его. Лимит обнуляется при перезапуске (ADR-0024).
- Посетители с выключенным JS и блокировщиками (если они режут запрос к `/api/v1/analytics/`) не считаются. Цифры — нижняя граница.
- Горячая строка (`PROFILE_VIEW` популярного профиля за день) обновляется под блокировкой строки. На текущем масштабе это незаметно; пересматривается, если запись событий станет заметной в задержке API.
- Таблица растёт на единицы строк в день на профиль; удаляется с аккаунтом.
- Отказ ручки или базы не виден посетителю: фронтенд не ждёт ответа.

## Риски

- **`keepalive`-запрос при уходе со страницы.** Демо и GitHub открываются в новой вкладке, и страница остаётся. Если где-то ссылка уводит текущую вкладку, запрос всё равно должен уйти. Проверяем в 7.3 в Chromium и Firefox по журналу сети и по счётчику в базе. Если теряется — обработчик ссылки ждёт запрос не дольше 300 мс.
